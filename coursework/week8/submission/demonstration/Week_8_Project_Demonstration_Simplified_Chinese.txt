第八周项目演示

本演示展示 Explainable AI Email Triage 应用程序作为一个受控的本地研究原型运行。该系统旨在协助人工审查可能紧急的电子邮件。它不会自主做出路由决定，也未获准进行影子测试或生产部署。

应用程序顶部的通知说明了最重要的边界。当前模型处置状态为 revise，并且每个结果都需要人工审查。Gate A 已通过，因为软件工作流程能够加载经过验证的本地工件、接受受限输入、返回可重复的结果，并在出现问题时安全失败。这个工程结果并不表示分类器已经通过单独的预测可靠性门槛。

在本次演示中，我使用的是完全合成的消息。主题是“合成截止日期提醒”，正文要求在今天下午三点之前完成审查。整个过程不会输入任何私人邮件、审查者备注、地址或其他个人信息。

现在我选择 Analyze。模型返回的紧急概率约为百分之四十九点五。在零点四五的分类门槛下，该消息被分类为紧急。在零点五零的分类门槛下，同一条消息被分类为非紧急。这个分歧正是界面要明确展示的主要发现。分类门槛的一个小变化就会改变结果，因此应用程序不会隐藏这种不确定性，也不会替用户选择操作门槛。

下一部分显示了在拟合的逻辑回归计算中支持紧急和非紧急两侧的特征。这些贡献有助于解释模型如何产生该分数。它们不是因果解释，也不能证明一封邮件为什么真正紧急。

Required handling 卡片确保人员仍然参与决策过程。结果继续标记为 revise，输入保留字段显示 no，部署批准也显示 no。应用程序返回供审查的研究结果，但不会路由消息，也不会保存提交的主题和正文。

经过验证的工作流程还包括安全失败行为。第二个本地实例被有意配置为一个不存在的模型路径。它的健康响应报告 not ready，并说明未找到本地研究工件。处置状态仍为 revise，部署和影子测试批准均保持 false。如果在这种状态下请求分析，服务会返回不可用响应，而不是加载其他模型或编造预测。我为这项检查使用了单独的路径和端口，因此经过验证的模型工件没有被删除、重命名或修改。

在准备这段录制之前，我重新运行了文档中记录的验证流程。全部十三项自动化测试都已通过。验证器还完成了六十次确定性的合成推理运行，并确认了可见阈值、受限解释、隐私安全输出以及仅限研究使用的工件边界。

本演示满足第八周展示人工智能模型实际运行的要求。它也保留了项目过程中建立的证据边界。软件已经能够进行可重复的本地演示，但在考虑任何操作建议之前，分类器仍然需要更多已标注数据、一个新保留且未接触的测试集，以及更有力的可靠性证据。

审查证据时，最好的起点是主 README 中链接的 Project Review Guide。该指南把 docs 文件夹中的书面结论连接到 results 文件夹中的精确 CSV 和 JSON 证据。第六周的 experiment record 支持阈值结论，第七周的 automated test report 和 demo validation 文件支持十三项测试和六十次推理的结果。demonstration runbook 说明如何复现应用程序和安全失败检查。通过这种结构，审查者无需在整个仓库中搜索，就能追踪演示中的每一项陈述。
